# 1. システム全体アーキテクチャ

## 1.1 全体像

```
┌──────────────────────────────────────────────────────────────────┐
│                        受験者 / 管理者ブラウザ                      │
│  Next.js (React + TypeScript)                                     │
│  ・受験ウィザード（論題→準備→録画→処理→レポート）                   │
│  ・MediaRecorder API による録画（webm: 映像+音声）                  │
│  ・管理者画面（論題管理 / 履歴 / 評価修正 / 設定 / PDF再発行）        │
└───────────────┬──────────────────────────────────────────────────┘
                │ HTTPS (REST API / SSE)
┌───────────────▼──────────────────────────────────────────────────┐
│  アプリケーションサーバ（Next.js API Routes + Worker プロセス）      │
│                                                                   │
│  ┌─────────────── ドメイン層（フレームワーク非依存） ───────────────┐ │
│  │  Assessment / Speech / Rubric / Evaluation / Report / Motion  │ │
│  │  RubricEngine（決定的採点エンジン）                             │ │
│  │  RoleSpec（PM / LO / …の役割定義 = データ駆動）                 │ │
│  └───────────────────────────────────────────────────────────────┘ │
│  ┌────────────────────── ポート（インターフェース） ────────────────┐ │
│  │ SttPort / TtsPort / JudgeLlmPort / VisionPort /               │ │
│  │ MediaSourcePort / StoragePort / PdfPort / QueuePort           │ │
│  └───────────────────────────────────────────────────────────────┘ │
│  ┌────────────────────────── アダプタ ──────────────────────────┐   │
│  │ OpenAI STT │ OpenAI TTS │ Claude(判定/生成/視覚) │ ffmpeg     │   │
│  │ S3互換ストレージ │ Playwright PDF │ pg-boss(ジョブキュー)      │   │
│  │ WebRecorder（MVP）│ Zoom/Teams/Meet（第2フェーズ以降）         │   │
│  └───────────────────────────────────────────────────────────────┘ │
└───────────────┬──────────────────────────┬───────────────────────┘
                │                          │
        ┌───────▼────────┐        ┌────────▼────────┐
        │ PostgreSQL 16  │        │ S3互換ストレージ │
        │ （全永続データ  │        │ （録画/音声:一時  │
        │  + ジョブキュー）│        │  PDF: 永続）     │
        └────────────────┘        └─────────────────┘
```

- **単一リポジトリ・単一デプロイ単位のモジュラーモノリス**を採用します。
  マイクロサービスは運用コスト・保守要員の観点で過剰であり、モジュール境界（ドメイン層/ポート/アダプタ）を
  厳密に保つことで将来の分割余地を残します。
- Web サーバと**ワーカープロセス**（採点パイプライン実行）を分離し、録画アップロード後の重い処理
  （ffmpeg / STT / LLM）がUI応答をブロックしないようにします。キューは PostgreSQL ベース（pg-boss）とし、
  Redis 等の追加インフラを不要にしてコストと運用負荷を抑えます。

## 1.2 採点パイプライン（非同期ジョブ）

```
録画アップロード完了
  → [job] extract    : ffmpeg で音声抽出（webm→wav/flac）+ 音量統計 + フレーム抽出(0.5fps)
  → [job] transcribe : STT（単語タイムスタンプ付き文字起こし）
  → [job] metrics    : 沈黙率 / 発話時間 / 話速 / 音量分布 を決定的に算出
  → [job] vision     : サンプルフレームから視線(カメラ目線率)・姿勢・ジェスチャーを判定
  → [job] judge      : LLM が「詳細項目の充足判定＋根拠引用」を構造化出力
                       → RubricEngine が点数・S/A/B/C・PD Level を決定的に計算
  → [job] comments   : Good Points / Improvement Points / Overall Comments 生成
  → [job] report     : PD Assessment Report (PDF) 生成・保存
  → [job] cleanup    : 録画・音声を削除（管理者設定「録画保存ON」の場合は保持）
```

- 各ジョブは冪等・リトライ可能（ステータスと成果物をDBに記録し、失敗時は該当ジョブから再実行）。
- **映像・音声の解析はすべて削除前に完了**させるため、Manner（アイコンタクト等）の判定材料
  （視線率・フレーム別判定結果・音響統計）は数値・テキストとしてDBに残し、メディア本体は削除できます。

## 1.3 将来拡張のための抽象化

### 録画ソース（MediaSourcePort）

| 実装 | フェーズ | 説明 |
|------|---------|------|
| WebRecorder | MVP | ブラウザ MediaRecorder → アップロード |
| ZoomAdapter | Phase 2 | Zoom Meeting SDK / クラウドレコーディング + Webhook |
| Teams / Meet | Phase 3 | Graph API / Meet API |

パイプラインは「動画ファイル＋メタデータ」を受け取る設計のため、ソースが変わっても
extract 以降のジョブは共通です。

### 役割（RoleSpec = データ駆動）

PM / LO / MG / MO / LOR / PMR の各役割は**コードではなくデータ**（DB + シード）で定義します。

```jsonc
// RoleSpec の例（PM）
{
  "role": "PM",
  "side": "government",
  "speechType": "constructive",
  "timeLimits": { "regulation": 180, "graceMax": 210, "minHalf": 90, "aMin": 150 },
  "requiredElements": [            // スピーチシート由来。judge プロンプトと評価観点に反映
    { "key": "definition",   "label": "定義（必要な場合）", "optional": true },
    { "key": "gov_point_1",  "label": "Government Point 1" },
    { "key": "gov_point_2",  "label": "Government Point 2" },
    { "key": "gov_point_1_detail", "label": "Government Point 1 の詳しい説明" }
  ],
  "inputs": []                     // LO は ["pm_speech"] を要求する
}
```

- LOR / PMR（Reply）はルーブリック上の時間閾値・詳細項目の［ ］表記が異なるため、
  ルーブリック定義側にも Reply 用の差分を持たせます（04-scoring 参照）。
- 新役割の追加＝ RoleSpec + PMスピーチ等の先行スピーチ生成設定の追加のみで済む構造とします。

### 言語（英語 / 日本語）

- 論題・生成スピーチ・STT・判定プロンプト・コメントの言語をアセスメント単位の `language` 属性で切替。
- ルーブリック定義は言語非依存（判定対象の言語だけが変わる）。
- MVP は英語ディベート + 日本語UI。

### AI プロバイダ

- STT / TTS / LLM / Vision はすべてポート経由。環境変数とDB設定でモデル・プロバイダを切替可能。
- 判定プロンプトとルーブリック定義は**バージョン管理**（DB保存）し、どのバージョンで採点されたかを
  評価レコードに記録します（再現性・監査性の担保）。

## 1.4 信頼性・セキュリティ

- 録画は非公開バケットに保存し、署名付きURLでのみアクセス。cleanup ジョブで確実に削除（削除日時を記録）。
- 個人情報は氏名・メールアドレスのみ（生年月日等は収集しない）。
- 管理者操作（評価修正・設定変更・再発行）はすべて監査ログに記録。
- LLM 呼び出しは JSON Schema による構造化出力＋バリデーション＋自動リトライ。失敗時はアセスメントを
  `failed` にして管理者に可視化（受験者には再受験を案内）。
- レート制御：同時採点ジョブ数の上限、受験者ごとの1日あたり受験回数上限（設定可能）。
